### Fixed

- **`@reticlehq/server` — a git worktree's flows, intents and runs land in that worktree, not the primary checkout.** Every worktree carries the same committed `.reticle.json`, so a daemon serving several of them saw one projectId for all, refused to choose (`AMBIGUOUS`), and fell back to its own directory — the primary checkout when it was started there. Flows saved while verifying a worktree never reached that worktree's branch, and `reticle gate` run there reported nothing covered. The tie is now broken by where the page was SERVED from: the dev server that announced the page's loopback port (the Vite plugin's `devserver-<port>.json`), otherwise the working directory of the process listening on it (`lsof`, so Next.js and any other framework too). The deepest checkout containing that directory wins, so a worktree nested inside the primary (`.claude/worktrees/x`) resolves to itself. Every session path — save, list, replay, heal, mutate, the suite, the run artifact and the cloud link — now carries the page origin with the projectId, so a flow is always read from the checkout it was written to, including with several worktree tabs connected at once. Where the serving directory cannot be observed (a remote page, no `lsof`), the answer is unchanged. No wire change: works with every SDK already installed. Closes [#1389](https://github.com/reticlehq/reticle/issues/1389).
